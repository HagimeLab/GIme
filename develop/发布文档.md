# GIme 发布文档

本文件规定 GIme 的**推送与发布**口径：什么时候可以推、推什么、推到哪、文稿怎么写、发布后怎么核。
代码构建细节见 `develop/开发文档.md`，验收口径见 `develop/验收文档.md`。

- GitHub：`HagimeLab/GIme`（源代码、`release/latest.json`、安装包、Release 资产）
- Gitee：`hagemilab/gi`（**只放安装包**，用于国内下载加速）

---

## 一、硬前提：必须由用户下达发布指令

**没有用户明确指令，不得执行任何对外动作。** 包括但不限于：

- `git push`（任何分支、任何 tag）
- 创建 GitHub Release / 上传 Release 资产
- 上传 Gitee Release / 在 Gitee 建 tag
- 把 `release/latest.json` 的版本声明推给远端（一旦推送，全体用户的「检查更新」立刻看到它）

### 1. 什么算「指令」

用户的指令必须同时表达**建包**和**推送/发布**两层意思，例如：

- 「打包并推送 1.1.8」
- 「建立安装包，发布到 GitHub 和 Gitee」
- 「发版」

以下**不算**发布指令，只能做本地动作：

- 「修一下这个问题」「跑一下测试」「先看看能不能编」→ 只改代码 / 只本地出包验证
- 「提交」→ 只本地 commit，不 push
- 「先别推送」「还有其他东西」→ 整批停在本地，未重新授权前不得发布

指令有歧义（版本号没给、要发的范围不清、是否连带未完成改动）时**先问**，不要自行决定版本号或范围。

### 2. 指令到达后先核对的四件事

| 项目 | 口径 |
|---|---|
| 版本号 | 用户是否指定？未指定则按「上一发布版本 + 0.0.1」提议并等确认 |
| 改动范围 | 只发布用户认可的那批改动；工作区里无关的未提交文件**不得顺手带走** |
| `versionCode` | 必须比上一版 +1（`versionName` 不升时 `Ver.isNewer` 会判「无新版本」） |
| 上一样本 | 运行 `tools\check.cmd` 与 `tools\check-release.ps1`，红的一律不推 |

> 已提交但用户裁定晚于该提交时：照实列在发布说明的「待裁/未做」里，不回改已提交内容。

## 二、推什么、推到哪里

一次发布是**同一批产物**分发到两个仓库，内容边界如下：

| 去向 | 内容 | 用途 | 是否必需 |
|---|---|---|---|
| GitHub `main` | 全部源代码 + `release/latest.json` + `release/GIme-v*.apk` | 源码交付；jsDelivr / raw 直出安装包 | 必需 |
| GitHub `tag vX.Y.Z` | 指向本次发布的那个提交 | 版本锚点、源码包生成基准 | 必需 |
| GitHub Release `vX.Y.Z` | ①安装包 `.apk` ②源码包 `-source.zip` ③正文（弹窗文稿） | 全体用户检查更新、手动下载 | 必需 |
| Gitee Release `vX.Y.Z` | **只有安装包 `.apk`** | 国内下载加速（客户端第一优先源） | 必需 |
| Gitee 源码/分支 | **不推送** | —— | 禁止 |

补充规则：

- 安装包同时**进 GitHub 仓库的 `release/` 目录**（jsDelivr 从仓库直出）**并**作为 Release 资产发布，两处字节必须相同。
- 源码包只作为 GitHub Release 资产，不单独进 Gitee。
- 签名材料（`signing/`、`*.jks`）、本机配置（`local.properties`、`build.local.cmd`）、构建产物（`build/`、`.gradle/`）**任何仓库都不进**。
- 一版一推：不要把多个版本的产物混在同一批资产里；旧包在归档时移出 `release/`。

## 三、版本号与命名规则

| 项目 | 规则 | 原因 |
|---|---|---|
| `versionName` | `X.Y.Z`，与 tag、文稿、清单完全一致 | 检查更新按版本名比较 |
| `versionCode` | 每版 +1（当前 1.1.7 是 18，下一版 19） | 覆盖安装与商店口径 |
| APK 文件名 | `GIme-vX.Y.Z-<SHA-256 前 8 位>.apk` | jsDelivr 对同一 URL 强缓存 7 天；路径随内容变才不会下发旧包 |
| tag | 轻量标签 `vX.Y.Z` | 与 Release、Gitee tag 同名 |
| 源码包 | `dist/GIme-vX.Y.Z-source.zip` | 内容 = tag 那棵树减去 `release/*.apk` |
| Gitee tag | **必须** `vX.Y.Z`，且附件名与 GitHub 上的 APK 名逐字相同 | 客户端按 `releases/download/v<版本>/<APK 名>` 拼地址，名字不一致就 404 |

`release/latest.json` 是**唯一真源**：`version` = 当前最高版本，`apk` = 仓库内安装包文件名，`notes` = 弹窗逐条说明。
GitHub API 的 `releases/latest` 只是老版本客户端的回落路径，不作为新版本的声明入口。

## 四、发布流程（按顺序执行）

### 步骤 0：定版

- `app/build.gradle.kts` 里 `versionName` 改为目标版本、`versionCode` +1。
- 确认签名配置未变（`signing/gime-release.jks`，与历史版本同一张证书，可直接覆盖升级）。

### 步骤 1：本地回归

```powershell
tools\check.cmd
pwsh -File tools\check-release.ps1
```

两条都全过才继续。`check.cmd` 里任何一项红，都先修再发，不靠「上次是过的」放行。

### 步骤 2：出包

```powershell
build.cmd
```

产物在 `app\build\outputs\apk\release\app-release.apk`，已用 `gime-release.jks` 签名。

### 步骤 3：归档安装包并更新清单

```powershell
# 关键：publish.ps1 会删除 release/ 下除本次 APK 外的所有 *.apk
# 若有候选包（如 *-candidate.apk）先移出 release/，否则会被一并删掉
pwsh -File tools\publish.ps1 -Apk app\build\outputs\apk\release\app-release.apk `
  -Version 1.1.8 -Notes notes.txt
```

- `notes.txt`：一行一条，与步骤 4 的文稿同源；也可用 `-Notes "第一条|第二条"` 形式。
- 脚本会：校验 `versionName` 与参数一致 → 复制为 `release/GIme-vX.Y.Z-<指纹>.apk` → 写出 `release/latest.json`。
- 幂等：同一份字节重复执行只跳过复制，不产生第二个文件。

### 步骤 4：写两份文稿

见第六、七节的格式。先写 `docs/vX.Y.Z-release-body.md`（短稿），再写 `docs/vX.Y.Z-发布说明.md`（长稿），
并确认 `latest.json` 的 `notes` 与短稿逐条一致（`verify-release.ps1` 会比对，不一致直接判失败）。

### 步骤 5：提交并推送 GitHub 源代码

```powershell
git add app docs release/latest.json "release/GIme-v1.1.8-xxxxxxxx.apk"
git commit -m "release: v1.1.8 打包（<构建提交短号>）"
git tag v1.1.8
git push origin main
git push origin v1.1.8
```

- 提交信息沿用仓库习惯：`release: vX.Y.Z 打包（<短号>）`。
- 推送前回读身份：`git log -1 --format="%an <%ae> | %cn <%ce>"`，必须是项目身份，不是本机默认身份。
- 若 `git push` 被网络掐断（本机常态），改用 API 逐笔重建：

  ```powershell
  node tools\push-commits.mjs HagimeLab/GIme main <远端当前 main 的 SHA>
  ```

  远端生成的 SHA 允许与本地不同（身份/签名字段），但最后必须做双向核对：仅本地 / 仅远端 / 内容不同三个数都为 0。
- tag 推不上去时，不要改写历史；由步骤 6 的 Release 在远端顺带建 tag，再把远端 tag 指向记进发布说明的「发布后补记」。

### 步骤 6：建 GitHub Release（安装包 + 源码包）

```powershell
pwsh -File tools\make-source-zip.ps1 -Out dist\GIme-v1.1.8-source.zip

node tools\make-release.mjs v1.1.8 1.1.8 docs/v1.1.8-release-body.md `
  release/GIme-v1.1.8-xxxxxxxx.apk dist/GIme-v1.1.8-source.zip
```

- 正文自动由短稿逐行加 `- ` 生成，末尾追加 `详细：docs/v1.1.8-发布说明.md`。
- 已存在同名 Release 时不重复建，只补传资产；同名资产字节相同则跳过，字节不同才删旧传新。
- 资产只应有两个：`GIme-vX.Y.Z-<指纹>.apk` 与 `GIme-vX.Y.Z-source.zip`。

### 步骤 7：建 Gitee Release（只传安装包）

见第八节。顺序放在 GitHub Release 之后，保证 Gitee 上的包与 GitHub、仓库内三处是同一份字节。

### 步骤 8：发布后核验

```powershell
pwsh -File tools\verify-release.ps1 -Tag v1.1.8 `
  -Apk release\GIme-v1.1.8-xxxxxxxx.apk -Source dist\GIme-v1.1.8-source.zip
```

必须全部通过，重点看四组读数：

1. 两个资产远端字节数 / SHA-256 与本地一致；
2. Release 正文与 `latest.json` 的说明都在 50–100 字；
3. `latest.json` 与 `docs/vX.Y.Z-release-body.md` 逐条同源；
4. 源码包内没有 `.git` / `build` / `signing` / 本机配置 / 密钥。

再补三项人工读数：

- Gitee 安装包地址 `HEAD` 返回 200，且 `Content-Length` 与本地一致（抽一次 `curl -I`）。
- jsDelivr 至少一个入口能下完整字节（`cdn` / `fastly` / `testingcf` / `gcore` 任一）。
- 旧版本升级语义：用 `Ver.isNewer("X.Y.Z", "X.Y.(Z-1)")` 及更早版本各判一次，均应为 `true`。

### 步骤 9：归档发布记录

在 `docs/vX.Y.Z-发布说明.md` 的「发布件」一节补齐（或沿用 v1.0.x 的 `-发布记录.md` 表格）：
Release 链接与 id、远端 tag 指向、源码包大小与 SHA-256、资产核对结果、Gitee 下载地址实测结果、回归计数。
**发布后才知道的读数单独起「发布后补记」一节**，不要回改已经被打进标签树的正文。

## 五、失败与补救

| 情况 | 处理 |
|---|---|
| 资产传了一半 / 上传超时 | 重跑 `make-release.mjs`，同字节会跳过，不同字节才替换 |
| 发现包有问题、已推送 | **不 force push、不改写已发布 tag**；升 `versionCode`，出下一个补丁版本 |
| `latest.json` 写错版本或文件名 | 本地改回并重新提交推送；`check-release.ps1` 会卡「清单声明 vs 目录实际」 |
| Gitee 附件名与 APK 名不一致 | 删除该附件重新上传；不要靠改客户端兜底 |
| 短稿超 100 字 | 删内部实现细节，保留用户可感知的变化；不要删 `docs/` 那一行（长度检查不计它） |
| 回归偶发失败 | 同条件重跑一次；第二次仍红按失败处理，并在发布说明里写明根因是否已复现 |

## 六、版本推送文稿格式（Release 正文 / 弹窗文稿）

**作用**：这段文字就是手机「检查更新」弹窗的正文。GitHub Release body 与 `release/latest.json` 的 `notes`
都从它来，**短稿是唯一来源**。

**文件**：`docs/vX.Y.Z-release-body.md`

**格式**：

```text
<用户可感知的变化一>
<用户可感知的变化二>
<用户可感知的变化三>
<用户可感知的变化四>
<用户可感知的变化五>
```

**规则**：

1. 一行一条，**不要自己加 `- `、不要写标题、不要 Markdown 加粗或链接**（`make-release.mjs` 会自动逐行加 `- `）。
2. 每条只写用户看到/用到的结果，通常 8–20 字；不写类名、文件名、函数名、内部机制。
3. 条数 3–6 条，默认 5 条。
4. 长度按**加前缀后**计算：
   - 设源文件每行去掉空白后的总字数为 `N`，行数为 `L`；
   - Release 正文会变成 `N + L`（`- ` 去空白后每行算 1 字）；
   - 要求 `50 ≤ N + L ≤ 100`。五条时源文件控制在 **45–95 字**。
5. 不写「详细：…」那一行，脚本自动生成。
6. 不写空泛词（「优化体验」「修复若干问题」），写清改前 → 改后的差别。
7. 与长稿（发布说明）的章节一一对应，不能出现长稿里没有的承诺。

**通过示例**（v1.1.7：短稿 77 字，加前缀后 82 字，在 50–100 内）：

```text
播放器：加载反馈/音量/手势/倍速/自动连播
切页自动暂停，回来继续
题库整叠卡片，左滑改名删除
分类卡去阴影，界面更干净
OpenUI 组件 35→43，图文更丰富
```

**不通过示例**：

```text
## 本次更新
- 重构了 Updater.java 的多源探测逻辑，把 probe() 的连接超时从 6s 调整为...
**修复**若干问题
```

（原因：带 Markdown、写内部实现、空泛、且超长。）

## 七、版本更新说明格式（长稿）

**作用**：给人看的完整说明，承载所有「改了什么、为什么、边界在哪、怎么验证」。Release 正文里的
`详细：docs/vX.Y.Z-发布说明.md` 指向它。

**文件**：`docs/vX.Y.Z-发布说明.md`

**结构模板**：

```markdown
# GIme vX.Y.Z

> 版本口径：vX.Y.(Z-1) 已发布（versionCode N，发布件 `release/GIme-vX.Y.(Z-1)-<指纹>.apk`，
> GitHub Release `vX.Y.(Z-1)`）。该版之后到本次定版之间的全部工作归 **X.Y.Z**（versionCode N+1）。
> 安装包由 `signing/gime-release.jks` 签名（与上一版同一张证书），可直接覆盖安装升级，
> 题库、做题记录、方案、对话历史都不动。

## 一、这一版做了什么（一句话版）

<两三句讲清本版主题与最大变化>

## 二、<主题 A>

- **<子项>**：改前是什么样 → 改后是什么样；用户可见的结果。
- **修复**：<现象> → <根因> → <现在的行为>。

## 三、<主题 B>

- ……

## N、未做 / 已知边界

- <明确不在本版范围的事项，以及原因>
- <未复现的异常：写「未复现 + 现有证据 + 根因未定位」，不要写「已修复」>

## N+1、发布件

- 出包：`gradle :app:assembleRelease`（R8 + `signing/gime-release.jks`）
  → `release/GIme-vX.Y.Z-<指纹>.apk`；`publish.ps1` 写入 `release/latest.json`（L 条说明），旧包移出 `release/`。
- 下发：安装包随源码进仓库，由 jsDelivr / GitHub raw 直出；Gitee Release 同步一份安装包；
  更新检查读仓库内 `release/latest.json`（唯一真源）。
- 兼容：versionCode N+1、minSdk 24、targetSdk 36；覆盖升级，数据保留。
```

**写法规则**：

1. 每条写「改前 → 改后」和用户可见结果；涉及取舍的写明代价。
2. 可以写实测读数（字节数、耗时、字数、测试项数），但不要拿量化结果替代结论。
3. 没有复现证据的异常，明写「未复现 / 待复测」，不冒充「已修复」。
4. 用户已经裁定不做的事，单列在「未做 / 已知边界」，不要偷偷塞回正文。
5. 长稿与短稿的条目必须能对上：短稿是长稿的压缩，不是另一份说辞。
6. 只在「发布后补记」里写远端已发生的事实（Release id、远端 tag、资产大小），正文保持「发布前可知」。

## 八、Gitee 侧规则（只放安装包）

### 1. 边界

- 仓库：`https://gitee.com/hagemilab/gi`
- **只放**：每个版本的安装包（Gitee Release 附件）。
- **不放**：源代码、`-source.zip`、`latest.json`、签名材料、候选包、构建产物。
- 原因：
  - 国内到 Gitee 的速度明显优于 GitHub，安装包放这里显著缩短下载时间；
  - Gitee 的 raw 只直出文本文件，`.apk` 会 403，所以**安装包必须走 Release 附件**，不能塞进分支目录；
  - 源码只保留一份真源（GitHub），避免两处代码漂移、也避免把源码面扩大到第二个平台。

### 2. 每版必须对齐的三件事

| 项目 | 要求 |
|---|---|
| tag | 恰好 `vX.Y.Z`（客户端由 APK 文件名反推版本后再拼 tag） |
| 附件名 | 与 GitHub Release 里的 APK **逐字相同**：`GIme-vX.Y.Z-<指纹>.apk` |
| 字节 | 与 GitHub 资产、仓库内 `release/` 下的包完全一致（同一份文件，不重新构建） |

客户端拼出的地址是：

```text
https://gitee.com/hagemilab/gi/releases/download/vX.Y.Z/GIme-vX.Y.Z-<指纹>.apk
```

任一条件不满足，这个源会 403/404，客户端会退到 jsDelivr —— 不会让更新失败，但**国内加速就失效了**。

### 3. 操作方式（二选一）

**方式 A：网页手动上传（推荐，最不容易出错）**

1. 打开 `https://gitee.com/hagemilab/gi/releases` → 新建发行版；
2. 标签名填 `vX.Y.Z`（无此 tag 时按页面提示基于仓库已有提交创建）；
3. 标题 `GIme vX.Y.Z`，正文粘贴**短稿**（与 GitHub Release 正文同款，带 `- ` 前缀）；
4. 上传附件，**只选** `release/GIme-vX.Y.Z-<指纹>.apk`；
5. 发布后点附件地址核对：下载大小与本地一致。

**方式 B：Gitee OpenAPI v5**

```powershell
# 令牌从环境变量取，不写进脚本、不贴进文档、不进 shell 历史
$env:GITEE_TOKEN = "<个人设置 → 私人令牌>"

# 1) 建 tag（仓库里没有 vX.Y.Z 时）
curl.exe -s -X POST "https://gitee.com/api/v5/repos/hagemilab/gi/tags" `
  -d "access_token=$env:GITEE_TOKEN&refs=main&tag_name=vX.Y.Z"

# 2) 建 Release
curl.exe -s -X POST "https://gitee.com/api/v5/repos/hagemilab/gi/releases" `
  -d "access_token=$env:GITEE_TOKEN&tag_name=vX.Y.Z&name=GIme vX.Y.Z&target_commitish=main&body=<短稿正文>"

# 3) 上传附件（只传 APK）
curl.exe -s -X POST "https://gitee.com/api/v5/repos/hagemilab/gi/releases/<release_id>/attach_files" `
  -F "access_token=$env:GITEE_TOKEN" `
  -F "file=@release/GIme-vX.Y.Z-<指纹>.apk"
```

> 当前 `tools/` 下没有 Gitee 上传脚本（`make-release.mjs` 只处理 GitHub），所以这一步按上面两种方式手动执行；
> 不要把令牌写进任何入库文件。

### 4. Gitee 侧核验

```powershell
curl.exe -sI "https://gitee.com/hagemilab/gi/releases/download/vX.Y.Z/GIme-vX.Y.Z-<指纹>.apk"
```

要求：`HTTP/1.1 200`，`Content-Length` 与本地 APK 字节数一致。再抽查一次实际下载的 SHA-256
（与 `release/latest.json` 同目录的那份文件比对）。

## 九、发布核验清单

发布完成 = 下面每一条都打勾，有一条空着就不算发完。

- [ ] 用户已明确下达「建包并推送」指令，范围与版本号已确认
- [ ] `versionName` = tag = 文稿版本 = `latest.json.version`
- [ ] `versionCode` 已 +1
- [ ] `tools\check.cmd` 全过
- [ ] `tools\check-release.ps1` 全过（含文件名指纹 = 实际 SHA-256 前 8 位）
- [ ] GitHub `main` 与本地 HEAD 零差异（仅本地 / 仅远端 / 内容不同 = 0 / 0 / 0）
- [ ] 提交身份正确（`%an/%cn` 为项目身份）
- [ ] GitHub Release 两个资产：APK + 源码包，字节与 SHA 与本地一致
- [ ] Release 正文 50–100 字；`latest.json` notes 50–100 字且与短稿逐条一致
- [ ] 源码包无 `.git` / `build` / `signing` / `local.properties` / `*.jks`
- [ ] Gitee Release `vX.Y.Z` 存在，附件仅 APK，同名、同字节，`HEAD` 200
- [ ] jsDelivr 至少一个入口 200 且 SHA 一致
- [ ] 旧版本 `isNewer` 判定全部为 `true`
- [ ] 发布说明已写「未做 / 已知边界」，发布记录已补「发布后补记」

## 十、禁止事项

1. 未收到用户指令就 push、建 Release、传 Gitee、或改动远端 `latest.json`。
2. 把源代码 / 源码包 / `latest.json` 推送到 Gitee。
3. 用固定名（如 `GIme-latest.apk`）作为发布件 —— jsDelivr 会缓存 7 天，用户永远装到旧包。
4. 重新构建后沿用旧文件名 —— 指纹进文件名就是为这件事。
5. 改了 `latest.json` 不同步短稿，或改了短稿不同步 `latest.json`。
6. 为了让字节数好看而删掉「未做 / 已知边界」。
7. 把内部实现细节写进弹窗短稿来凑长度。
8. 顺手提交工作区里与本版无关的改动、候选包或本机配置。
9. 已发布后发现问题就 force push / 改 tag / 覆盖资产 —— 一律出新补丁版本。
10. 把 Gitee 或 GitHub 的令牌写进脚本、文档、命令行参数或提交记录。
