# GIme 验收文档（验收前必读）

> 制定：2026-10-31 · 配套 develop/开发文档.md
> 验收 = 按下述四层逐项做完并分层汇报，任何一层缺失都算验收未完成。

## 一、四层验收标准（缺一不可）

### 第 1 层 · 动态回归

- `tools\check.cmd` 全量执行，**全绿且退出码 0** 才算过；出现红灯先判定是代码缺陷还是本机环境偶发（单独复跑定位），环境偶发须复跑证实后才可放行并注明。
- 本周期新增的回归项须逐条点名确认覆盖了本次改动面（不允许只靠旧用例过绿）。

### 第 2 层 · 真机冒烟（含活体发送，已获长期授权）

- 真机安装本周期 debug 包，启动无崩溃（logcat 无 FATAL / Uncaught）。
- 变更涉及大肥鱼/模型路径的，**直接在真机上真实发送测试消息**——用户已授权（2026-10-31："以后测试都可以进行发送"），无需逐次请示；额度由用户承担。
- 操作优先走 WebView CDP 通道（地址与用法见开发文档 §二），比盲点坐标可靠；断言用页面真实状态（chatBusy、chatMsgs、DOM 节点），不要只看截图目测。
- 测完把设备恢复原状：回首页、主题复原、`adb forward --remove-all`。

### 第 3 层 · 全界面 UI 走查（合理性 + 美观度）

- **每个界面都截真机图**：首页、题库、错题本、我的、答题页、对话面板（含 OpenUI 卡片特写），**浅色与深色主题各走一遍**；截图留档（会话目录 ui_shots*/，按界面编号命名）。
- 逐张目检，禁止只看几何数据下结论。检查维度：
  - 合理性：布局对齐、间距节奏、内容溢出/裁切、层级遮挡（浮层/tab 栏/滚动到底）、信息密度；
  - 美观度：黑白灰新拟态一致性、深浅主题下所有新控件是否正确换肤、圆角/阴影是否沿用令牌风格；
  - 新功能与既有界面的融合度（如新组件的气泡内外边距、与 Markdown 混排表现）。
- 发现问题：能当场定级的写"缺陷/建议"，并逐条登记到 §五 对应版本记录——它们是**下个方案的第一输入**。

### 第 4 层 · 版本一致性核验（对开发文档规则 3）

- **"已发布"判定：已推送 GitHub 且 release/ 安装包已更新；仅本地 git 提交不算发布，未发布周期内所有批次工作（P0/P1…）同属一个版本号。**
- 验收必查项：`git log --oneline -8` + `app/build.gradle.kts` 的 versionName/versionCode，核对三件事：
  1. 本周期改动确实落在"最近已发布版本 +1"上（例：最新提交发布是 v1.1.2 → 本周期必须且只能是 1.1.3）；
  2. 提交历史里没有越权动作：不得出现 `release:` 提交、GitHub push 痕迹、release/ 目录变化、发布说明/更新包文件——除非用户在本次明确指示过；
  3. 工作区未提交内容与开发文档 §六 版本快照一致；不一致就当场更新快照或指出偏差。

## 二、红线（与开发文档规则 2 同源）

- 验收者**不得**执行：`git push`、GitHub Release 操作、`publish.ps1`/`make-release.mjs`/`verify-release.ps1`、制作或更新安装包。只有用户**亲自发消息**说"提交并发布新版本"才允许，一次授权一次动作。
- 验收过程中不得修改任何业务代码——发现缺陷记录并汇报，修不修、何时修由用户决定。

## 三、汇报格式（每次验收按此结构输出）

```
① 动态回归：结果 + 红灯归因（如有）
② 真机冒烟：安装/启动/活体发送结论（消息内容、耗时、渲染证据）
③ UI 走查：逐界面 深浅 × 结论，问题清单（界面/严重级/现象/截图号）
④ 版本一致性：git log + versionName/Code 核对结论
遗留与待办：未提交项、环境偶发项、下方案输入
```

## 四、跨版本问题闭环（对应用户要求）

- 每个验收周期结束，§五 追加一条记录：版本、四层结论、**问题清单（含严重级与截图证据号）**。
- 下个开发方案（plan/vX.Y.Z-plan.md）的**第一章节必须为"上版验收问题说明"**：逐条引用上版问题，写明"本方案修复/延后（理由）"，不允许静默丢弃。
- 修复完成的条目在下一轮验收第 3 层复验后才可标记关闭。
