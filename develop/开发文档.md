## 一、三条铁律（每个周期必须遵守，无例外）

### 规则 1 —— 修改流程：本地测试 → 真机测试 → 才允许提交本地 git

严格按顺序，不允许跳步：

1. 写代码；
2. **本地测试完毕且成功**：`tools\check.cmd` 全绿且退出码 0 + `build.cmd` 编译通过（改了什么就至少覆盖对应的回归项）；
3. **真机测试完毕且成功**：`adb install -r` 安装 debug 包，启动无崩溃，变更路径在真机上实际走一遍（操作 + 截图 + logcat 佐证）；
4. 以上两步全部通过后，才允许 `git commit`（本地仓库）。

- 真机测试失败：修复或回退，**禁止**把"只是本地过了"的代码提交进去。
- 一批改动含多个主题时拆成多个提交，每个可独立回滚（参照 P0 的 C1–C5 切分）。
- 禁止用 `git commit` 顺手带 `git push`：push 是 GitHub 动作，受规则 2 约束。

### 规则 2 —— 不推 GitHub、不做发布包，除非用户当下明确说明

- 以下动作默认**永远不做**，只有用户在当次对话里明确说"推送/发布/出包"才执行，历史授权不延续到新版本：
  - `git push` 到 GitHub、创建或修改 GitHub Release；
  - `tools/publish.ps1`、`tools/make-release.mjs`、`tools/verify-release.ps1`；
  - 整理新版本更新方案、制作/更新 `release/` 目录里的安装包与发布说明。
- 拿不准"用户是不是这个意思"时，先问，再动。

### 规则 3 —— 动手前先查已发布的版本号，据此定本周期版本

- **"发布"的唯一判定标准：已推送到 GitHub 并更新了 release/ 安装包。本地 git 提交、本地定版（改 versionName）都不算发布。**
- 判定法：**最近已发布版本 +1 个小版本 = 本周期修改版本**；同一未发布周期内的多批工作（如 P0、P1）全部归入同一个版本号，versionName/versionCode 不再变化。
  例：v1.1.2 已发布；v1.1.3 只是本地定版+提交、GitHub 上还没有 → P0、P1 的工作都仍属于 1.1.3。只有 v1.1.3 被推送 GitHub 并发布安装包之后，下一周期才是 1.1.4。
- 开工前必做：`git log --oneline -8` 查最近 `release: v...` 提交，并核对 GitHub/release/ 里最新安装包版本，两者一致才算"已发布"。
- `versionName/versionCode` 在未发布周期内只在首次定版时写一次；跳号、升大版本、定新发布版本号，都只在用户指示发版时确定。

## 二、工具链与真机通道

- JDK / Android SDK / Gradle 路径全部取自根目录 `build.local.cmd`（不入库），换机器先重建这个文件。
- 本地回归：`tools\check.cmd`；完整构建：`build.cmd`（产出 debug + release）。
- adb 在 `%ANDROID_HOME%\platform-tools\adb.exe`；设备序列号会闪断，命令前先 `adb wait-for-device`，进程号取 `adb shell pidof com.fan.shuatiku`。
- WebView 调试（debug 构建可用）：
  ```
  adb forward tcp:9333 localabstract:webview_devtools_remote_<pid>
  http://127.0.0.1:9333/json          # 取页面 ws 地址，Runtime.evaluate 驱动页面
  ```
  仓库自带 `tools/device-cdp.mjs` 为只读断言参考；走查/活体可写会话级临时脚本，不入库。
- 日志标签：`adb logcat -s GImeMCP GImeBridge GImeNet`（MCP 口令在 GImeMCP 启动行里打）。
- 推送只能走 `node tools/push-commits.mjs <repo> <branch> <远端头> [本地共同祖先]`：本机到 github.com 的 git 通道被重置，
  远端头若是 GitHub 网页提交（带 gpgsig）本地拉不到对象，就用第四个参数给本地祖先算清单（每笔 tree 仍以远端父 tree 为 base）。
  推完脚本打印 `HEAD_SHA`，**本机 `origin/main` 无法对齐**（远端对象不在本地库，`git update-ref` 会拒），
  下次推送以上一次打印的 `HEAD_SHA` 为 `<远端头>`。

## 三、前端结构（P0 拆分后，新代码必须按此放置）

- `index.html` 只是骨架；样式 → `style.css`；核心状态/路由/主题/练习判分 → `app-core.js`；题库管理/导入/统计/设置/更新 → `app-admin.js`；方案域（首页 Hero、方案库/详情、MCP 计划工具） → `app-plan.js`；大肥鱼对话（含 mdToHtml、OpenUI 挂载） → `app-chat.js`；OpenUI → `ui/openui-core.js`（官方 bundle，**不要手改**）+ `ui/openui-ui.js`。
- 脚本加载顺序固定：bank.js → ui/openui-core.js → ui/openui-ui.js → app-core.js → app-admin.js → app-plan.js → app-chat.js；新增脚本必须排在依赖之后。
- 全局函数跨文件共享：新增函数前必须做**跨文件同名查重**（P0 基线 332 个函数仅 2 处历史同名且在闭包内）；顶层 `var/let/const` 不得与既有顶层名重复。
- 主题只允许使用既有令牌（--paper/--surface/--raise/--ink/--ink-2/--ink-3/--line/--ok/--sh-*/--sink/--r-card/--ease），禁止硬编码颜色；任何新组件必须在浅色与深色主题下都能看。

- 「发出后没反馈」两处修（2026-11-02，用户反馈）：
  ① **读盘消息一律算答完**（`chatSettleRestored`，启动两条分支 + 切会话共三处读盘口）。
     回答中途 App 被杀掉时，收尾前已经 `chatSave()` 过一次，`live:true` 会被写进盘；
     读回来若不清掉，`chatHasLive()` 从此恒真，而 `chatRender` 里等待气泡的条件是
     `chatBusy && !chatHasLive()` ⇒ 「大肥鱼正在想…」那颗泡**永久不再出现**，发出到第一个字之间屏幕上是空的。
     顺带修掉另一个后果：带 `live:true` 的消息按流式分支画，正文不解析 Markdown（星号露在外面）。
  ② **链没摊出字时仍显示打字泡**：上一笔摊帧引入的回归——`hasThink` 看的是全量链，
     链刚到、`shownThink` 还是 0 的那一瞬间，空的思考盒把打字泡顶掉了。改成看摊出的视图（`!!thinkView`）。
- 附件入口分两项（2026-11-02）：回形针不再直接拉文件选择器，先弹一个小浮窗「发给大肥鱼」——
  **上传文件** 走原来那条抽取链路（PDF/docx/md/txt → 本地抽文字 → 分段上行），
  **上传图片** 走相册多选（`pickChatImages` → `ACTION_OPEN_DOCUMENT` + `EXTRA_ALLOW_MULTIPLE`，`image/*`），
  只回**缩略图**（最长边 160px、JPEG 60，一张几 KB），原图一个字节都不上行。
  选中的图落在输入框上方一排缩略图（点 × 撤一张，最多 6 张），配不配文字都能发；
  发出去后缩略图随消息记录、气泡里显示，输入区清空。
  上游口径：两条通道都没有视觉能力，所以只给模型一行「【图片附件】共 N 张：a.jpg、b.jpg」的说明，
  并明确写「你看不到图片内容，不要描述/猜测/编造」；这条说明**单独成一条 system**，
  不并进 `attachMeta`——那条一非空就会进「导入文档」的结算口径（`fileRun`）。
- 网页版真看图（2026-11-02，用户裁定走「复刻网页版文件引用」）：DeepSeek 网页版的完成请求本来就有
  `ref_file_ids` 字段（以前恒发空数组）。现在图片是真的传上去再引用的：
  ① `POST /api/v0/file/upload_file`（multipart，字段 `file`，带 `x-thinking-enabled / x-model-type / x-file-size`，
     **PoW 必须按这个 target_path 单独算**——`powHeader(referer, targetPath)` 已参数化，PoW 一次性不能复用）；
  ② 返回 `data.biz_data.id`（`file-<uuid>`），再 `GET /api/v0/file/fetch_files?file_ids=<id>` 轮询到 `status=SUCCESS`
     （PENDING/PARSING 每 1.5s 一次，最多 20s；FAILED/CONTENT_TOO_LONG 等直接判失败）；
  ③ 完成请求的 `ref_file_ids` 只挂**第一轮**（后续工具轮靠上游会话链），只在登录通道挂（API Key 那条没有网页会话）。
  上传的是压缩后的图（最长边 1600、JPEG 85），文件名保留图片扩展名——上游按扩展名判类型，白名单里有 png/jpg/jpeg/heic/webp/bmp/gif/tiff 等。
- 图片说明的分寸（2026-11-02，真机踩坑）：**只有 id 到手才写「图已随消息提供，可以直接看图」**；
  没传上去时**一句话都不写**（只在本机 toast）。原因：这条说明会随 prompt 进上游会话历史，
  写「你看不到图」之后，后面真带图的轮次模型还在复读「我看不到」——本轮真机实测被自己的说明带偏过一次。
- 图片边传边等（2026-11-02，用户裁定）：图片**一放进输入区就开始上传**，不再等点发送。
  多选是**一张一张来**（`chatImagePump`，上一张回包才走下一张），每张有自己的状态：
  `up`（缩略图 `filter: blur(4px)` 模糊 + 按钮变「上传中」并禁用）/ `ok`（清晰，可发）/ `err`（模糊 + 红色 `!`）。
  **上传中不许发送**（会缺图），但**允许点 × 撤图**——撤掉的正好是在传那张时，队列自动接下一张。
  发送时直接用已经到手的 `file id`，不再现传；有图没传上去就只发文字并在本机提示，不往会话里写说明。
- 上传进度用「清晰从上往下露出来」（2026-11-02，用户裁定）：缩略图分两层——底层始终模糊，上层清晰，
  用 `-webkit-mask-image: linear-gradient(to bottom, … var(--p))` 按进度从上往下放出来，露到哪儿就是传到哪儿。
  进度是**真字节数**：`HttpNet` 分块写（32KB 一报）、Cronet 用自定义 `UploadDataProvider` 每读一段回报，
  原生按「≥4% 且 ≥150ms」节流后推 `window.onChatImageProg(idx, pct)`；只改那一张的 `--p`，不整块重画。
  传到 99% 就停，最后的 100% 由「解析完成」那条回调给（`ok` 状态）。
  ⚠️ 踩坑：`getLength()` 给了定长后 Cronet 按**非分块**走，`onReadSucceeded(true)` 会抛
  `Non-chunked upload can't have last chunk`，上传必失败——定长上传永远传 `false`（回归里钉住了）。
- 附件浮窗三点收口（2026-11-02）：① 浮窗背后铺 `.att-scrim`（z 999，夹在对话 990 与浮窗 1000 之间），

## 七、文档目录与 GitHub 推送边界

| 目录 | 放什么 | 进 Git / 推送 |
|---|---|---|
| `develop/` | 开发文档、验收文档 | 进 Git，随代码提交 |
| `docs/` | 版本发布说明、接口说明、版本记录 | 进 Git，随代码提交/发布 |
| `plan/` | 本地周期方案 | **不进 Git**（`.gitignore` 已忽略），不参与任何 GitHub 推送 |

- `plan/` 为本机自建目录：`git add`、`git commit`、`git push` 以及发布脚本的 GitHub 文件白名单都不得包含它。
- 周期方案直接写在 `plan/` 里；需要公开的接口/发布说明写进 `docs/`，不要把方案内容混进 `docs/`。
