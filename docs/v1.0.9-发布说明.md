# GIme v1.0.9

> 版本口径：v1.0.8 已发布；这一版是 **伪装加强版**，versionCode 10，versionName 1.0.9。
> 目标不是“保证不封”，而是把 v1.0.8 里最明显的结构性破绽——UA 自称 Chrome、底层却不是浏览器 TLS——补上。

## 一、传输层换成 Cronet

v1.0.8 的 API/HIF 请求走 `HttpURLConnection`：平台 Conscrypt 的 ClientHello，ALPN 只有
`http/1.1`，UA 却写着 Chrome 120。WAF 只要看握手就知道不是浏览器。

v1.0.9 引入 `org.chromium.net:cronet-bundled:500.1.0`（native 版本 **155.0.8059.16**，
statically linked），所有 DeepSeek API / HIF 请求改走 Cronet：

- Chromium 的 BoringSSL ClientHello、ALPN **h2**、HTTP/2 帧序；
- 关闭 QUIC（`enableQuic(false)`），统一 h2，避免 h3 与浏览器画像不一致；
- 保留原有的超时、首帧看门狗、用户“停止”、Cookie 回收、SSE 方言解析；
- Cronet 的异步回调用 Piped 流包成同步 InputStream，桥接层代码不需要感知；
- 回调失败不会静默截断：`FailureInputStream` 在 EOF 时把上游错误翻成 IOException；
- 只打包 `arm64-v8a` / `armeabi-v7a`，去掉用不到的 x86 so。

桌面回归仍然可用：`HttpNet` 是薄抽象，Android 上安装 Cronet 实现，桌面/测试没有 Cronet 时
自动回退 `HttpURLConnection`，所以 `DeepSeekClientTest` 等不需要 Android 运行时。

## 二、身份自洽

两条链路各自说一套完整的话，不再互相冒充：

| 链路 | UA | Client Hints | 握手 |
|---|---|---|---|
| 原生 API / HIF | 真机型号 + Android 版本 · Chrome/155.0.8059.16 | `Google Chrome`/`Chromium` 155、Android | Cronet 155 |
| 登录 WebView | 设备型号 · 引擎真实版本 Chrome/80.0.3987.132 | 不带（Chrome 80 本来就不发） | WebView Chromium 80 |

登录 WebView 的 UA 改为 `WebSettings.getDefaultUserAgent()` 里读出的引擎版本，去掉 `; wv`
与 `Version/4.0`，不再用一份 Chrome 120 的字符串去盖住 Chrome 80 的引擎。
原生 UA 也不再写死 Pixel 7 / Android 13：启动时用 `Build.MODEL` / `VERSION.RELEASE`
注入，和登录 WebView 报的是同一台设备；Chrome 版本仍各自对齐自己的引擎。

completion body 补了 `source` 字段。实测上游只接受 `default` / `landing`：
传 `input` 会回 422 `unknown variant`，所以固定用 `source:"default"`。

## 三、真机实测

测试机：Android 11、arm64（WebView Chromium 80）。

- Cronet 初始化：`Cronet version: 155.0.8059.16, arch: aarch64, source: Statically Linked`。
- 指纹体检（用 Cronet 请求 `tls.browserleaks.com/json`）：
  - JA3：`090e18a94158a024691e72e3b53ae59f`
  - JA4：`t13d1516h2_8daaf6152771_806a8c22fdea`（ALPN 已是 h2）
  - HTTP/2 Akamai：`1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`
  - 对照 v1.0.8：JA3 `9b02ebd3a43b62d825e1ac605b621dc8`，只有 http/1.1。
- 登录自检：`verify start token=64 cookie=318` → `verify result mobile=true`，0.46s 自动返回。
- 内置通道完成请求：POST body 2995B → `200 text/event-stream`，回复 `2`；
  `hif leim=73,dliq=0,attached=true`（dliq 在本网络不可达，和 v1.0.8 一致）。
- `create_pow_challenge` 200、`chat_session/create` 200、Completion 200 均由 Cronet 发出。
- 真机测试后已恢复测试前的会话/设置/进度；测试创建的网页会话已删除。

## 四、流式显示与主题图标

**电话登录的流式看起来“没有了”**：抓日志确认 Cronet 的读回调是连续的，但上游经常把
正文攒到最后一次性下发（一次 100~200 字）。数据没丢，只是气泡一口气砸出来。

修复（纯页面显示层，不改网络与已保存文本）：
- 新增 `liveText` / `pokeLive`：新到的正文按剩余量分帧摊开，最多约 8 帧（~250ms）；
- 收尾时先让 `shown` 追上全量，再关 `live` 并切 Markdown，最后一大段也不会瞬移；
- 用户停止/工具轮次丢弃气泡时，`chatDrop` 会同时停掉摊开计时器。

**深色→浅色时底部大肥鱼图标闪烁**：初次修复把两套头像叠放并预解码，但旧版 WebView 的回退转场仍会闪。
原因是浅色 `.reveal` 快照嵌在旧主题的 `<html data-theme="dark">` 下，祖先深色选择器仍会命中快照；
底层主题落定时，快照里的鱼图才切成浅色。

修复：
- 两张头像改为叠放（`position:absolute`），只切 `opacity`，两张始终参与渲染；
- 启动时对 `agent-light.png` / `agent-dark.png` 各 `new Image()` + `decode()` 预解码；
- 在浅色 `.reveal` 内覆盖底部导航、答题入口和对话头像的主题选择，按快照自身主题显示。

此前真机检查确认两张头像均 `complete/naturalWidth>0`，透明度会随主题切换；这次补上回退快照的主题作用域覆盖。

## 六、代价与限制

- **APK 变大**：debug 从约 3.1MB 涨到 15.9MB（Cronet native so 约 11MB）。release 同样量级。
- Cronet 版本与 UA/CH 是绑定的：升级 `cronet-bundled` 时必须同步改 UA/CH 和实测记录。
- 登录 WebView 是 Chromium 80，原生 API 是 Chrome 155：两条链路各自自洽，但版本不同。
  这是这台设备 WebView 无法升级的折中；若能把 WebView 升到新版本，两者可以更靠近。
- 传输层虽然已是浏览器同源，但**没有页面资源/埋点流量**，和真实网页仍有差距；
  同源 WebView 传输是下一步可选项。
- 仍然不能保证不封。行为画像（请求量、会话生命周期、device_id 关联）和网络出口同样重要。
